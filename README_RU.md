# Прототип ADAS системы — **ACC + AEB + LKA** в BeamNG.tech
([ENG](README.md) | [РУС](README_RU.md))

Исследовательский прототип усовершенствованной системы помощи водителю на базе
[BeamNG.tech](https://documentation.beamng.com/beamng_tech/), симулирующий автомобиль
который удерживает свою полосу, используя камеру + пайплайн компьютерного зрения.

**Статус (v1.0):** Система удержания полосы (LKA) работает.
ACC / AEB / CREEP внедрены в проект, но на данный момент зависят от радара, который нуждается
в дальнейшей настройке и улучшениях - они включены в дорожную карту v1.1.

**Замечание:** BeamNG.tech поставляется со [встроенным LKA][beamng-lka].
В этом проекте LKA реализован с "нуля" (камера → CV-пайплайн → контроллер)
в учебных целях — целью было построить весь стек от восприятия до управления, 
а не просто настроить "готовое решение" встроенное в симулятор.

[beamng-lka]: https://documentation.beamng.com/beamng_tech/adas_features/lane_keeping_assist/_index_en/

```
   ┌─────────┐    ┌─────────────┐    ┌──────────┐
   │Пайплайн │    │ Дистанция,  │    │Скорость, │

   └────┬────┘    └──────┬──────┘    └─────┬────┘
        │                │                 │
        └────────────────┼─────────────────┘
                         ▼
                  ┌─────────────┐
                  │  Измерения  │ (фиксация всех показаний датчиков в рамках одной итерации цикла)
                  └──────┬──────┘
                         ▼
                  ┌─────────────┐
                  │   State     │  CRUISE/FOLLOW/AEB/
                  │   machine   │  CREEP/STOP
                  └──────┬──────┘
                         ▼
                  ┌─────────────┐
                  │ Контроллеры │  PID + LPF + slew rate
                  │  состояний  │  + gain scheduling
                  └──────┬──────┘
                         ▼
                 vehicle.control()
```

Система разделена на четкие уровни:

- **Восприятие** — `lane_detection.py`: ROI (зона интереса) → преобразование перспективы (bird's-eye) →
  HLS-бинаризация → sliding window → аппроксимация полиномом 2-й степени → sanity checks →
  смещение относительно полосы в метрах.
- **Sensor fusion** (лёгкое) — `ADASController.measure()`: объединяет полученное с камеры
   смещение в полосе с дистанцией от радара/ультразвуковых датчиков в фиксации `Measurements`
   данных.
- **State machine** — чистая функция `next_state()`: CRUISE / FOLLOW / AEB / CREEP / STOP
  с логикой подтверждения по тактам и гистерезисом для предотвращения ложных переключений.
- **Управление** — `compute_steering()` и контроллеры газа/тормоза для каждого состояния;
  построены на базе универсального PIDController с защитой от интегрального насыщения (anti-windup)
  и ограничением выходного сигнала.

## Пайплайн удержания в полосе:

```
кадр с камеры (RGB)
    │
    ▼
Кроп зоны интереса (45–95% высоты кадра) - убираем небо и капот а/м
    │
    ▼
Перспективное преобразование (откалиброванные SRC_POINTS_FRAC)
    │
    ▼  вид bird's-eye (400×400)
HLS-бинаризация (белый и жёлтый диапазоны)
    │
    ▼
Метод скользящего окна или поиск на основе предыдущего кадра
    │
    ▼
np.polyfit 2-й степени - для каждой линии
    │
    ▼

Проверки на достоверность:
  - параллельность (коэффициенты «a» достаточно близки)
  - ширина полосы в пределах [0.3×BEV, 1.5×BEV]
  - |смещение| < ширина_полосы / 2
  - |Δсмещение| < MAX_JUMP между кадрами

    │
    ▼  
	если линия теряется и/или плохо видна: резервный сценарий (fallback)
	→ восстановление по одной из линий с высокой достоверностью + априорной ширине полосы

    │
    ▼
lane_offset_m (со знаком: + = автомобиль правее центра)
```

Этот резервный сценарий (fallback) был добавлен после того, как на практике выяснилось:
прерывистая разметка часто дает меньше пикселей, чем сплошная правая линия края дороги.
Детектор сохраняет сглаженное априорное значение `lane_width_px_prior`
и использует его для геометрического восстановления более слабой линии.

## Инженерные моменты достойные упоминания:

Это баги и тупиковые ветки разработки, о которых стоит рассказать — именно они
определили итоговую архитектуру системы.

### Знак управляющего сигнала руля: дважды инвертирован

Сначала ПД-регулятор использовал ошибку `error = ego_x` и работал, потому что на
карте `tech_ground` автомобиль спавнился в начале координат. Переход на управление
относительно полосы (`error = lane_offset_m`) и смена карты изменили результирующий
знак: автомобиль стал резко уходить в сторону от центра вместо того, чтобы
возвращаться к нему. Диагностику удалось провести через анализ CSV-логов –
значения `offset` и `steering` имели одинаковый знак на каждом замере,
что бывает только при положительной обратной связи.
Проблема решилась добавлением одного знака «минус».

### "ПИД кажется хуже, чем ПД" - Дифф. составляющая (D) усиливает шум датчиков

Даже после настройки gain scheduling управление оставалось дерганным: Δsteer
осциллировало на ~6% от диапазона каждый тик. Причина: `lane_offset_m` рассчитывалась
на основе зашумленных данных с CV-пайплайна, где межкадровые скачки составляют 0.1–0.2 м.
Дифф. составляющая (D-term) делит скачок на `dt = 0.02 s`, выдавая большие значения производной,
которые бросают управляющее воздействие из одной крайности в другую. Решением стало
**почти полное зануление D** (`KD = 0.05`) и увеличение постоянной времени фильтра нижних частот (LPF)
на выходе. Фактически система превратилась в ПИ-регулятор с мощным выходным LPF.

Вывод: D отлично работает на **сглаженных** сигналах, но на зашумленных данных она начинает
работать против вас.

### «Фантомы» радара оказались асфальтом и другими деталями окружения


Изначально радар выдавал ложные срабатывания на дистанции ~1.6 м, вызывая
ложные торможения. В качестве временного решения радар был просто развернут вверх.
Позже, путём диагностики (`radar_inspect.py`) было выявлено, что радар возвращает
~36,000 ray hits за такт - это «сырые» данные - при стандартном поле зрения в ±34° по обеим осям.
Ближайшие попадания лучей были просто поверхностью дороги прямо перед бампером.
Правильное решение состоит из двух этапов:
- Настроить датчик на реалистичное поле зрения (`field_of_view_y=6`, `half_angle_deg=12`),
- Фильтровать оставшиеся лучи по углу места, азимуту и интенсивности перед применением `argmin`.

Эта задача запланирована на v1.1.

## CREEP - медленное подползание к остановившейся цели

CREEP - состояние, которое активируется, когда радар видит цель в непосредственной близости
и эта цель не движется. Вместо того чтобы бесконечно держать тормоз (что помешало бы
начать движение в потоке, когда идущая впереди машина наконец тронется), CREEP запускает
небольшой ПИ-регулятор, который поддерживает низкую скорость (~5 км/ч).
Машина медленно продвигается вперед, контролируя показания переднего ультразвукового датчика.
Если дистанция сокращается до `US_STOP_DIST`, система возвращается в STOP; если же ведущий
автомобиль уезжает вперед, система переключается обратно в FOLLOW.

Мне очень хотелось реализовать функцию из реальных систем ADAS - плавное
следование за машиной в режиме пробок, поэтому я встроил это поведение
напрямую в state machine.

## Как запустить:

### Необходимые компоненты

- **BeamNG.tech** v0.38.5 (исследовательская версия, не потребительская BeamNG.drive)
- Python 3.10+
- Python-библиотеки из requirements.txt

### Установка зависимостей

```bash
pip install -r requirements.txt
```

### Запуск

```bash
# Без визуализации (меньше нагрузка CPU)
python "adas-v1.01 (visualizer).py"

# С визуализацией
python "adas-v1.01 (visualizer).py" --visualize
```

По умолчанию скрипт запускает BeamNG.tech, загружает карту `automation_test_track`,
спавнит ego-машину на прямом участке дороги и запускает CRUISE со скоростью,
определённой в `Config.TARGET_SPEED`.

Нажмите Ctrl+C в консоли, чтобы остановить симуляцию. Подробный лог каждого тика
записывается в `adas_log.csv`.

## Ограничения:

- Калибровка детекции полосы (`SRC_POINTS_FRAC`) настроена вручную под конкретную позицию
  камеры, установленную на данном автомобиле для данной карты. Другие позиции / карты / машины
  потребуют повторной калибровки с помощью `camera_test.py` + `calibrate.py`.
- Пайплайн предполагает, что дорожная разметка присутствует и отчетливо видна.
  Стертая краска, тени или ночное время ухудшат качество детекции — данные сценарии
  не тестировались.
- Работа алгоритмов проверялась только на дорогах с твердым покрытием и корректной разметкой.
  Бездорожье, гравий и подобные дороги не входят в рамки проекта.
- В v1.0 радар отключен обходным методом (`dir=(0,0,1)`). ACC/AEB заложены в коде
  и покрыты юнит-тестами, но на практике они не будут работать до выхода v1.1
  с корректно настроенным радаром.
- Коэффициенты рулевого управления настраивались для скоростей 9–40 км/ч.
  На 60+ км/ч gain scheduling снижает KP, однако тестирование на шоссейных скоростях не проводилось.
